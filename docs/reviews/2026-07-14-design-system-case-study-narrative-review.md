# Design System Case Study — UX 敘事審查

> 審查日期：2026-07-14
> 審查範圍：[Design System Case Study](https://hmingdesign.com/zh-TW/design-system-case-study) 全頁敘事
> 語氣基準：[Advantech](https://hmingdesign.com/zh-TW/advantech)、[Crypto Arsenal](https://hmingdesign.com/zh-TW/crypto-arsenal)
> 本文件只做內容與資訊架構審查，不包含 code 或 UI 修改。

## 整體判斷

這份 case study 的優勢不是「做了很多設計變數、共用元件和文件」，而是 Hming 能從畫面意外跑版與文件脫節中找出系統問題，建立「哪些內容適合共用、哪些應保留單頁彈性」的判斷準則。三個演化實例尤其有辨識度，能呈現設計系統判斷，而不只是展示元件目錄。

目前最大的問題是：讀者必須先走過大量專案內部流程，才看到產出與價值。10 個同層 TOC、反覆出現的 AI workflow／治理描述，以及大量名詞註釋，使頁面更像內部技術紀錄，而不像 recruiter 能在 1–2 分鐘掌握的 UX case study。Outcome 雖然有數字，但多數是產出數量，不是成效證據。

建議保留核心內容，但把主線收斂為：

> 作品集持續擴張 → 規則分散與修改風險增加 → 盤點實際上線網站找到問題 → 建立共用與單頁保留的判斷框架 → 用 3 個案例驗證框架 → 透過治理與檢查維持一致 → 說明目前成效與下一步。

## 優先級總覽

### P0 — 最影響 recruiter 閱讀

1. 將 10 個同層 TOC 收斂為 6 個主章節，Evolution A／B／C 改為同一主章下的子案例。
2. 把 Outcome 的摘要移到頁面前段，先回答「做完後有什麼不同」，再進入過程。
3. 合併重複的 AI workflow、governance、validation、reflection 內容，避免同一觀點出現 4–5 次。
4. 將「268 個設計變數、19 個共用元件、10 份文件、3 項檢查工具」明確標為已完成的產出；若要稱為實際成效，需補前後差異或成功避免問題的證據。
5. 將主敘事從「我怎麼管理 AI」拉回「我如何維持設計一致性、敘事彈性與可維護性」。AI 是方法之一，不應成為整篇的第二主角。

### P1 — 提升可信度與語氣一致性

1. 將絕對、宣言式或較口語的句子改為可驗證的描述。
2. 統一中英文標題與術語層級，避免 TOC 中中文、英文與字母編號混用。
3. 精簡每節的「名詞註釋」，只保留理解決策所必須的術語。
4. 補清楚自發專案的使用者與利害關係人：主要使用者是網站訪客、未來維護者，還是 Hming 自己？三者需求不同。
5. 說明持續迭代中的時間界線，讓讀者知道哪些已完成、哪些仍在進行。

### P2 — 內容精修

1. 每個主章開頭只留一句重點摘要，不要連續用兩到三段引言重述標題。
2. 刪除 Git 操作層級的細節，例如完整的 `audit → implementation → validation → smoke → commit → push` 六步說明；濃縮成「小範圍修改、驗證、可回溯版本」即可。
3. Reflection 收斂為 2–3 個真正新增的學習，不再重述 Turning Points。

## TOC 層級審查

### 目前結構

1. 為什麼要建 Design System
2. 起點
3. 三次轉折
4. 決策框架
5. 演化實例 A
6. 演化實例 B
7. 演化實例 C
8. Governance 與 AI 協作
9. Outcome
10. Reflection

### 問題

- 10 個項目全部同層，讀者看不出「主線」與「證據案例」的差別。
- `Evolution A / B / C` 是同一組框架的三個證據，不應佔據三個一級章節。
- `三次轉折`、`決策框架`、`Governance` 都在解釋方法與規則，彼此界線不夠清楚。
- `Outcome` 排在第 9，recruiter 必須讀完大部分頁面才知道成果。
- 中文、英文與意思不夠直接的標籤混用；Advantech 和 Crypto Arsenal 的 TOC 多使用直接的專案階段名稱，掃讀成本較低。

### 建議 TOC

1. **專案總覽**
   - 問題、角色、範圍、目前成果摘要
2. **現況與挑戰**
   - 規則分散、文件與實際網站脫節、修改意外破壞原有畫面
3. **設計原則與決策框架**
   - 哪些規則適合集中管理、哪些版型適合整理成共用元件、哪些設計應保留在單一頁面
4. **三個演化案例**
   - Before / After 版型：確認模式穩定後才整理成共用元件
   - 反思卡與多重對比：刻意保留為單頁專用設計
   - Button / LinkButton：先釐清語意
5. **治理與驗證**
   - 文件、ownership、檢查機制；AI-assisted workflow 僅作為其中一項方法
6. **成果與反思**
   - 已完成的產出、已驗證的改善、限制、下一步

這個結構把讀者需要理解的主線從 10 段縮成 6 段，同時保留三個最能展現判斷力的案例。

### 通用說法原則

這份 case study 面對的不只有設計師與工程師，也可能包含 HR、recruiter、產品主管與其他領域的面試官。主敘事應先用一般讀者能理解的說法，再視需要於括號補上專業術語。不要要求讀者先理解團隊內部用語，才能看懂 Hming 做了什麼。

| 團隊內部或技術說法 | 建議的通用說法 |
| --- | --- |
| 抽元件 | 整理成共用元件 |
| 不抽元件 | 保留為單頁專用設計 |
| 抽象 | 將重複內容整理成可共用的規則或元件 |
| 過早抽象 | 太早把還沒穩定的設計整理成共用方案 |
| Local component | 單頁專用元件 |
| Token 化 | 把重複使用的顏色、間距或字級集中管理 |
| Component contract | 元件的使用規則與適用範圍 |
| Slot-based composition | 固定共用結構，但讓各頁替換自己的內容 |
| Production code | 實際上線網站的程式實作 |
| Regression | 修改後意外破壞原本正常的畫面或功能 |

建議寫法：

> 當相同的結構與行為在多個頁面穩定出現，我才會整理成共用元件；如果只是視覺相似，但承載的內容與用途不同，就先保留為單頁專用設計。

專業術語仍可保留，但順序應是「白話說明在前，術語在後」。例如：「固定共用結構、讓各頁替換內容（slot-based composition）」，而不是先丟出術語再另外要求讀者查看名詞解釋。

## Storytelling flow 審查

### 現在的敘事走向

目前的敘事大致是「動機 → 第一版 → 踩坑 → 流程 → 框架 → 三個案例 → 治理 → 數量 → 學習」。時間順序合理，但價值揭露太晚，而且中段多次停下來解釋術語與工作流程，削弱了前進感。

### 建議的敘事節奏

#### 1. 先讓讀者理解問題的代價

現有開場說「設計散落在每一頁」，方向正確，但還缺少後果。可更直接交代：

- 相似版型在案例頁重複實作。
- 文件與實際網站不一致。
- 大範圍修改曾造成邊框重疊、間距跑掉與手機版水平溢出。
- 因此每次更新都增加重複修改與破壞既有頁面的風險。

這會比先談「想把理解落到真實作品」更接近 UX case study 的問題定義。

#### 2. 提前給出結果摘要

在總覽結尾先放 3–4 個結果摘要，但要分清楚「完成了什麼」與「帶來什麼改善」：

- **已完成的產出**：集中管理的設計變數、共用元件、規格文件、自動檢查工具。
- **已觀察到的改善**：多少案例頁改用共用結構、哪些錯誤被檢查工具攔下、哪些重複樣式被移除、更新某一版型時需要修改的檔案數是否下降。

若目前沒有完整前後數據，應誠實寫「目前已完成的系統範圍」，不要把項目數量包裝成實際成效。

#### 3. Turning Points 只保留因果，不先展開完整解法

三次轉折適合用作故事骨架，但目前第三個轉折已完整解釋 workflow，後面 Governance 又再講一次。建議每個轉折只回答：

- 原先假設是什麼？
- 發生了什麼問題？
- 決策因此怎麼改變？

詳細治理方式移到後面的「治理與驗證」。

#### 4. 把三個 Evolution 案例當成框架的證據

這三段是全頁最有價值的內容，因為它們同時呈現：

- 看見相似不代表要立刻整理成共用元件。
- 會評估語意、結構、行為與維護成本。
- 能說明採用與不採用的理由。

每個案例應維持相同模板：`情境 → 選項 → 判斷依據 → 決定 → 結果／限制`。目前 Evolution A 偏時間步驟、B 偏誘惑／判斷／決定、C 偏長文論證，結構不一致，會增加閱讀成本。

#### 5. Outcome 要回答「系統是否真的改善問題」

目前 Outcome 回答的是「系統裡有什麼」。Recruiter 更想知道：

- 更新共用 pattern 時，維護範圍是否縮小？
- 文件與實際網站是否能持續同步？
- 有沒有實際攔下錯誤或避免畫面、功能被意外破壞的案例？
- 4 個案例頁在一致性與個別敘事間如何取得平衡？
- 還有哪些範圍未完成？

## 與 Advantech、Crypto Arsenal 的語氣一致性

### 兩個既有案例的共同語氣

Advantech 與 Crypto Arsenal 都有幾個清楚特徵：

- 開場先說使用者／產品問題與後果。
- 說明 Hming 的角色與負責範圍。
- 以研究或既有流程作為決策依據。
- 把設計方案連回使用者任務。
- 清楚區分已完成、驗證結果與下一步。
- 口吻偏務實，重點放在「問題—判斷—方案—證據」。

### Design System case study 的差異

- 內部流程與 AI 協作篇幅明顯較高，主角有時從設計問題變成工作方法。
- 口語轉折較多，例如「規劃是規劃，code 是 code」、「一個都不抽」、「把搞懂寫下來，才算真的懂」。這些句子有個性，但比另外兩案更像心得文章。
- 技術／治理術語密度較高，且反覆加名詞解釋，閱讀節奏比 Advantech 與 Crypto Arsenal 更碎。
- Outcome 使用項目數量，Crypto Arsenal 則有任務時間、測試人數、易用性與質化回饋；兩者的證據強度不同，不應用同一種成果語氣。

### 建議語氣

保留第一人稱與學習歷程，但比照另外兩案，優先寫：

> 我觀察到什麼問題 → 我依據什麼做判斷 → 我做了什麼取捨 → 目前能證明什麼 → 還不能證明什麼。

不要把 Design System 寫成完成度或能力宣言；把它定位為一個持續迭代、已經產生實際規則與驗證機制的自發專案，會更可信。

## 重複內容盤點

| 重複主題 | 出現位置 | 建議 |
| --- | --- | --- |
| AI 需要明確邊界 | Hero、Why、Turning Point 2／3、workflow、Governance、Reflection | Hero 只列職責；Turning Point 說問題；Governance 說方法；Reflection 不再重述 |
| audit → implementation → validation | Turning Points workflow、Governance、Outcome guardrails、Reflection | 完整流程只留 Governance；其他段落用一句話回扣 |
| 以實際上線網站為現況基準 | Why、Turning Point 1、Outcome | 分清楚「實際網站是現況驗證基準」與「設計變數檔案是規則的管理來源」 |
| 不要太早整理成共用方案 | Turning Point 2、Framework、Evolution A、Evolution B、Evolution C | Framework 定義原則；Evolution 只放不同證據，不再重講原則 |
| 文件能讓協作一致 | Why、Starting Point、Governance、Reflection | 集中到 Governance，其他位置刪或縮成因果句 |
| 名詞註釋 | 幾乎每一章 | 只保留真正阻礙理解的 4–6 個詞；其餘改成首次出現時的白話說明或頁尾 glossary |
| 學到的三次轉折 | Turning Points、Reflection | Turning Points 說決策變化；Reflection 只留新的限制與下一步 |

## Objective language 審查

### 需要調整的句型

| 現有說法 | 問題 | 建議方向 |
| --- | --- | --- |
| 「這套系統和一般做法比較不一樣的地方」 | 「一般做法」沒有比較基準 | 「在這個專案中，我另外把 AI 任務的範圍與驗證條件寫入協作文件」 |
| 「系統建好只是開始，更重要的是它能不能防止之後慢慢走樣」 | 合理問題，但後續數字未證明「防止」 | 改為「為了降低規則再次分散的風險，我加入三類自動檢查」 |
| 「讓 AI 協作可以被管理、驗證與回溯」 | 說法空泛，缺少可觀察行為 | 指出任務範圍、檢查條件、預覽版本與可回復版本分別解決什麼風險 |
| 「結論是一個都不抽」 | 「抽」是團隊內部用語，且容易像戲劇化宣言 | 改為「這一輪盤點的 8 個版型都暫時保留為單頁設計」，並補上盤點範圍與判斷條件 |
| 「自創詞只有自己懂」 | 過度絕對 | 「自創詞增加了與工程討論時的解釋成本」 |
| 「把『搞懂』寫下來，才算真的懂」 | 像個人格言，與另外兩案語氣不同 | 「把定義與使用條件寫成文件，幫助我發現原先沒有釐清的邊界」 |
| 「268 個 runtime design tokens」 | 數字大不一定代表好，可能讓人擔心過度複雜 | 補分類、使用範圍、重複值是否下降；否則只列為系統規模 |
| 「19 個共用元件支撐 4 個案例頁」 | 只能說明採用範圍，不能直接代表成效 | 若能證明，補「哪些重複結構被整併、需要分別維護的位置減少多少」 |

### 需要釐清的名詞

- **Single source of truth**：頁面同時把實際網站與 `styles/tokens.css` 稱作唯一依據。建議分成「實際網站是現況驗證基準」與「tokens.css 是設計變數的管理來源」。
- **Outcome**：目前內容較接近「完成的項目與採用範圍」。若沒有實際使用結果，標題可改為「系統範圍與防護機制」。
- **Rule of Three**：先用白話說明「相同需求穩定出現多次後，再評估是否整理成共用元件」，並將 Rule of Three 放在括號中作為補充；不要暗示它是唯一或普遍標準。
- **Product Designer**：這是自發 side project，建議補一句說明 Hming 同時負責設計系統規劃、文件與前端驗證，避免角色與執行內容看起來不一致。

## Recruiter readability 審查

### 30 秒掃讀時能理解的內容

- 這是一個為個人作品集建立 Design System 的自發專案。
- Hming 負責系統規劃、元件盤點、文件與前端驗證。
- 專案處理重複樣式、元件邊界與修改風險。

### 30 秒內仍不容易理解的內容

- 最終到底改善了什麼，而不只是新增了什麼。
- 三個 evolution 案例中哪一個最能代表 Hming 的設計判斷。
- AI workflow 為什麼對 recruiter 重要，以及它與一般版本控制流程有何不同。
- 哪些數字是已驗證成效，哪些只是目前規模。
- 專案目前的完成度與下一階段目標。

### 建議的掃讀層

頁面應讓 recruiter 只讀以下內容也能理解故事：

1. Hero：一句問題與一句結果。
2. Overview：角色、範圍、限制、3 個成果摘要。
3. 每個主章的一句重點摘要。
4. 三個 evolution 案例的「決定」與「結果」。
5. Outcome：已驗證證據、限制、下一步。

名詞定義、完整 workflow、治理條目與技術細節則作為第二層內容，不應阻斷主線。

## 建議保留的內容

- Hero 的核心定位：「把自己的作品集當產品做」。
- 「網站不是沒有設計，只是設計散落在每一頁」這個問題 framing。
- 文件與實際網站脫節、未先盤點影響範圍的大幅修改造成畫面異常，這兩個真實轉折。
- 「重複的是值／殼／整件事」的決策框架，但建議壓縮用字。
- Evolution A／B／C 的具體案例。
- Button、Link、LinkButton、CTA 的語意判斷案例。
- Governance 中「文件內容必須對應實際上線功能」與「尚未有真實使用情境的元件暫緩建立」兩個決策。
- 對限制與持續迭代狀態的誠實說明。

## 建議刪除或大幅濃縮的內容

- 每一章都出現的名詞註釋。
- Git 操作的六步驟逐項說明。
- 重複解釋 AI 任務權限的段落。
- Reflection 中重述 Turning Points 的前兩項。
- 無法證明成效、只增加技術密度的 token／script 細節。
- 「一般做法」「真正懂」「一定」「每一次」等沒有明確範圍的絕對說法。

## 建議補強的證據

若資料存在，優先補以下任一種，不需要為了數字而製造數字：

1. 某個共用 pattern 改版前後，需要修改的檔案或 selector 數量。
2. validation scripts 實際攔下的錯誤案例。
3. 4 個案例頁實際採用共用元件的範圍，而非只列元件總數。
4. audit 前後，hard-coded color／spacing 或重複 pattern 的變化。
5. 主要螢幕寬度下，修改前後是否出現畫面異常的對照。
6. 文件項目與實際上線元件的對照結果，例如 30 項中多少項需要移除或修正。
7. 維護者完成一項常見更新所需步驟是否減少；若只有 Hming 自己使用，可用任務紀錄作為質化證據。

## 建議的新版敘事摘要

可用以下內容作為後續改稿方向，不代表需要逐字採用：

> 隨著作品集案例增加，相似版型、顏色與間距開始在各頁重複，設計文件也逐漸與實際網站脫節。一次未先盤點影響範圍的大幅修改，進一步造成間距、邊框與手機版水平溢出。為了降低後續維護風險，我重新盤點實際網站，建立「集中管理設計規則、整理共用元件、保留單頁彈性」的判斷框架，並用三個實際案例說明何時適合共用、何時應保留原本設計。最後，我把規則整理成與實際網站一致的文件與自動檢查，讓後續修改能在明確範圍內被驗證。

這段比目前 Hero 更接近 Advantech 與 Crypto Arsenal 的敘事方式：先交代問題與後果，再說方法與結果，同時避免把 AI 協作寫成主題本身。

## 建議執行順序

1. 先確認新版 6 段 TOC 與每段唯一任務。
2. 將現有內容標記為「保留／合併／移動／刪除」，先處理重複，不急著逐句改寫。
3. 定義 Outcome 可誠實使用的證據；沒有前後數據的項目改列 Outputs。
4. 統一語氣與術語，再做段落精簡。
5. 最後用 30 秒、2 分鐘、完整閱讀三種模式檢查 recruiter 是否能掌握同一條主線。

## 最終結論

這份 case study 不缺內容，缺的是取捨。最值得保留的是「從真實的畫面異常中，建立哪些內容適合共用、哪些應保留單頁彈性的判斷準則，並用三個案例說明取捨」；最該降低的是 AI／Git 流程、重複名詞解釋與產出數量的篇幅。完成收斂後，它可以比現在更像一份呈現系統思維與設計判斷的 UX case study，而不是一份設計系統建置日誌。
